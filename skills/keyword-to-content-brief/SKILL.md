## Two entry points / 两种使用入口
Use the [fillable bilingual questionnaire and exact JSON mapping](QUESTIONNAIRE.md) with the [runnable JSON template](INPUT.template.json). The questionnaire implements, rather than replaces, the [canonical intake](../../docs/business-intake.md).

- **AI-guided:** read skill + existing brief first → ask up to three missing questions → user answers → explicitly map answers to JSON → analyze and finish/review the report. Unknown answers remain valid; do not front-load the full worksheet.
- **CLI:** copy and edit JSON, never Python → run the noninteractive helper → inspect automatic report mode and next questions → amend JSON and rerun to a new output directory as needed. CLI produces evidence and scaffolds, not a finished editorial report.

问卷不会自动导入脚本，需要用户或 AI 按字段映射为 JSON。明确 unknown 不会重复追问；省略的必要字段才可能出现在 next_questions。两种方式均沿用同一业务提问规范和报告门，详见问卷使用步骤。

If enough is known, proceed with authorized read-only analysis without mandatory reconfirmation; ask only gaps, conflicts and time-sensitive essentials. A host without memory uses the brief. ## Codex planning entry point

For a seed keyword, supplied URL, existing strategy, or request for a full cluster plan, read [Codex cluster routing](references/codex-cluster-routing.md) and [the port/capability guide](../../docs/CODEX-CLUSTER-PORT.md). These are natural-language task routes, not installed slash commands. Keep this repository available so its relative references and scripts resolve. Discover the actual host tools before using them; do not assume Claude commands, plugin wrappers, home-directory paths, blog skills or paid providers exist.

The full planning route is: reuse authorized context and ask gaps → discover/expand candidates or import strategy → classify intent → collect/import qualified evidence → review page grouping and existing coverage → select pillar/spokes → assign templates and adjustable length budgets → design justified internal links → render plan JSON/Markdown and self-contained interactive HTML → produce individual briefs → review a planning scorecard and preserve revisions. Use the old offline path below when the request is limited to supplied-evidence page decisions. The two input formats are distinct; the old questionnaire remains the business-intake source, not an automatic new-module importer.

Live research is conditional on actual runtime tools, source permissions and user scope. Generic web search can discover candidates and competitors but is not automatically an ordered Google top-ten organic snapshot. Missing qualified evidence produces provisional topic architecture with overlap unknown, never a fabricated SERP-validated cluster. Unknown search volume remains null; first-party Search Console impressions are not market search volume.

Article writing, publication, GSC/Ads/DataForSEO connectors, blog execution and Google/PDF reporting are optional external capabilities, not included implementations. Do not imply an integration exists because upstream mentions it. This port's execution deliverable is briefs plus a planning scorecard; it does not claim articles were written, live links implemented or rankings improved.

## Existing-site decision gate

Before rendering, follow [inventory and context contract](../../docs/INVENTORY-CONTEXT.md). Supply a sourced page inventory, candidate destination and assessed coverage where known; use the supported --page-mapping adapter for an existing candidate_id/existing_url mapping file. Do not infer an empty site from absent inventory. Same-target consolidation is work deduplication, not a claim of measured SERP equivalence. Review possible topic duplicates even when wording differs. Missing or ambiguous coverage stays review_existing or defer; only complete inventory plus a sourced gap and business rationale can support new_proposal. No disposition authorizes site changes. Current page content assessment remains an agent/human task, not automatic crawling or semantic coverage verification.

For a recruitment portfolio, use explicit content_purpose=recruitment_portfolio and review role/reader-job fit. Preserve the supplied next_action, distinguish it from a measured conversion event and do not turn career evidence into product sales. Inspect the generated disposition counts, destination and template before handoff; generated scaffolds are not actionable modifications.

## Business intake before any recommendation
Read ../../docs/business-intake.md (EN/中文). Reuse the user's brief and supplied answers; never ask a question already answered. Ask at most three missing essentials in the first turn, grouping related fields naturally. Start with industry/offer, audience/market/language and the concrete decision plus primary objective. Then ask only relevant branches about positioning, brand/product lifecycle, conversion event, capacity/constraints, intent and existing content. Do not front-load a long mandatory interview. Record whether each answer is supplied, assumed or unknown with source IDs. “Unknown” is a valid answer, not a reason to refuse the report.

Choose report mode explicitly: tailored only when essential context is supplied and positioning is at least explicitly qualified; industry_general when industry is known but essential context remains incomplete; generic_framework if industry is unknown. An industry-general report still has reference value: organize supplied intent and content, compare possible objectives, show evidence gaps and next validation. Do not invent industry norms, market share, demand or ROI. Tailored does not imply ready to commission: missing keyword-priority, page-content or search-result evidence still limits individual decisions.

For awareness, discuss education/category understanding and brand associations rather than assuming a sales CTA. For consideration, use decision criteria and verified proof. For conversion, define the exact completed event and measurement, not just “more conversions.” For retention, consider customer adoption/help tasks. Treat brand, nonbrand and competitor terms separately; ask whose entity a navigational term refers to rather than assuming a product login. Mixed intent needs reader-job clarification. Distinguish the product/brand lifecycle from website age. Never infer brand leadership from the user's confidence, SERP presence or website age. Unknown positioning can produce a limited report; assumed positioning remains explicitly qualified.

## Existing offline evidence path
1. Check provenance, market/language/device/date, unique organic result URLs, and whether fixtures are synthetic. Normalize exact duplicate keywords while preserving their original IDs. Classify intent with reasons; supplied intent is an analyst hypothesis, not measured truth. Flag conflicting duplicates rather than silently selecting one.
2. Run `python scripts/plan_keywords.py INPUT.json --out OUTPUT_DIR` from repository root. This creates an auditable pair matrix, conservative same-page groups, page decisions, and brief scaffolds. This helper does not infer intent or write final briefs. Inspect warnings and deferred groups before using output.
3. Review every merge and separate-page decision. Seven shared top-10 URLs is upstream's heuristic, not a statistical guarantee. This adaptation requires compatible snapshots and every pair within a same-page group to meet the threshold (no transitive chain merges). Scores 4–6 suggest a topical relationship, 2–3 a possible cross-link, not a mandatory content page or link. Mixed intent may require separation despite overlap. No observed evidence means no automatic merge.
4. Reconcile inventory: a mapping means review_existing, not update. Only a cited page-content gap plus complete business context and an objective-linked priority can support an update proposal; covered pages are retain. Conflicting URLs need review, never silent redirects/deletes. Consolidate production/review work by target path, preserving separate group IDs and unverified keyword relationships. New-page priorities need a supplied rationale tied to the primary objective, brand role/funnel stage, compatible market/language and complete snapshot. Unknown priorities remain null. Cap new pages; separately estimate review/update/approval effort against stated resources before proposing a schedule. Numeric new-page capacity does not authorize updates or prove total capacity.
5. Produce editorial output with explicit sections: business context and report mode → supplied evidence → recommendations or reference guidance → assumptions/limits → next validation. Clearly tell users that an industry-general report remains useful for reference when they cannot supply a concrete problem. Include objective, lifecycle, positioning evidence status, conversion definition when relevant, resources and unresolved questions. Then provide decision table with input IDs, evidence IDs, overlap, reasons, uncertainty and next action; a brief for each selected page (primary/secondary keyword, reader job, title/meta suggestion, H2/H3 outline, key points, evidence needed, claims not allowed, relevant internal links and acceptance criteria). A scaffold is not a completed writing brief. Write the brief from the supplied business facts, not keyword substitution. Don't promise article word-count or link-count targets improve rankings.
6. Save first output before review. Review factual grounding, competing intent, duplicate targets, missing evidence, capacity and links. Record actual findings and corrections; retain an unchanged first pass even if it passes. Preserve before/after artifacts. Set final status `needs_human_review`, unless an actual human approval is supplied. Separate automated checks from editorial judgments and SEO outcomes.

## Boundaries
No network calls or paid services in either Python helper. The Codex agent may research and propose keyword candidates through available authorized tools; generated candidates are hypotheses, never measured demand. No article publication, backlink outreach, unsupported live rank claims, or traffic forecasts. Supplied SERP exports can be stale, incomplete or personalized; even ten results do not establish demand. Synthetic cases demonstrate procedure only. Real use needs current licensed exports, actual inventory, product-claim verification and an editor's decision.

Brand/product lifecycle can differ: use brand_lifecycle and product_lifecycle separately when needed; lifecycle is the shared planning context, never inferred from website_stage. 品牌与产品阶段不同则分别填写 brand_lifecycle 和 product_lifecycle，不能用网站年龄推断。
